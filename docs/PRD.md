# Record Tips 工程化 PRD

## 1. 文档说明

- 文档版本：v0.1
- 文档状态：Draft
- 目标平台：iPhone 优先，后续再考虑 iPad / Web 管理端
- 来源主题：将个人对话/想法通过 iPhone 语音输入，并逐步沉淀成个人知识库的应用
- 说明：原分享页正文存在 Google 动态校验限制，本 PRD 基于可识别题意进行工程化落地与范围补齐

## 2. 一句话定位

面向高频思考与表达的人群，提供一个从语音捕获、自动转写、结构化提炼到长期可检索回顾的个人知识库 App。

## 3. 产品判断

### 3.1 机会判断

这个方向有前景，但机会不在“再做一个录音机”，而在“把零散语音变成可复用知识资产”。

成立的前提有三点：

1. 捕获门槛足够低，用户能在走路、通勤、开会后、灵感出现时立刻记录。
2. 记录结果不是一段难以回看的长录音，而是自动被整理成摘要、观点、任务和主题。
3. 后续可搜索、可回顾、可合并，形成真正持续增长的个人知识库。

### 3.2 切入判断

更适合先做一个高价值、小人群、高频使用的工具型产品，而不是一开始做面向大众的内容社区。

首批切入人群：

- 独立开发者、创作者、研究者
- 顾问、销售、管理者等高频口头表达工作者
- 已经有 PKM 习惯，但嫌打字记录太重的用户

## 4. 背景与问题定义

当前用户在“记录想法”这件事上存在四类典型问题：

1. 输入摩擦高：想到内容时常处于无法打字的场景，导致想法流失。
2. 录音不可用：语音备忘录只能存素材，后续很难整理和检索。
3. 笔记断层：从瞬时想法到长期知识之间缺少自动整理链路。
4. 回顾成本高：用户无法快速回答“我之前在哪次表达过这个观点”。

## 5. 目标用户与核心场景

### 5.1 目标用户

| 用户类型 | 特征 | 核心诉求 |
| --- | --- | --- |
| 独立开发者 / 创作者 | 想法密度高，边走边想，产出依赖素材积累 | 快速记录、后续可直接转为内容或产品思考 |
| 管理者 / 顾问 / 销售 | 会后复盘多，表达内容分散在语音里 | 自动整理重点、任务和结论 |
| PKM 用户 | 已使用 Obsidian/Notion/Readwise 等 | 希望有更轻量的语音入口，而不是手工二次整理 |

### 5.2 核心场景

1. 通勤或散步时，用户对某个主题连续思考，想快速记录。
2. 开会或通话结束后，用户希望把口头复盘沉淀为结构化结论。
3. 用户做日更、播客、写作或产品设计时，需要持续积累原始观点。
4. 用户过几天想找回某次表达过的想法，需要通过搜索快速定位。

## 6. 社区与竞品启发

基于该题意对应的市场方向，可以得出几个重要判断：

1. 纯录音工具价值有限，用户真正需要的是“录完以后自动可用”。
2. 自动转写只是底层能力，决定留存的是结构化质量与检索体验。
3. 用户会高度关注隐私、导出能力和供应商锁定风险。
4. 如果产品不能帮助用户形成长期回顾闭环，录音最终会堆积成新的信息垃圾。

### 6.1 竞品空白

| 产品类型 | 优势 | 短板 | 对本产品的启发 |
| --- | --- | --- | --- |
| 语音备忘录类 | 记录快、使用门槛低 | 缺少结构化和知识沉淀 | 必须把“可回收利用”做到位 |
| 会议转写类 | 转写能力成熟 | 更偏多人会议，不适合个人长期知识积累 | MVP 不应从会议纪要切入 |
| PKM 笔记类 | 知识组织能力强 | 移动端捕获成本高 | 需要做语音优先入口 |
| AI 总结类 | 总结快 | 容易一次性消费，难形成长期知识网络 | 需要做持续累积和主题关联 |

### 6.2 市场结论

存在明确 niche 机会，但产品要先证明以下闭环：

- 用户愿意每周持续使用语音记录
- 自动整理结果足够值得回看
- 搜索与回顾能显著提升用户对历史内容的复用率

## 7. 产品目标

### 7.1 业务目标

1. 验证“语音驱动的个人知识库”是否具备稳定周活。
2. 建立从捕获到沉淀再到检索的完整使用闭环。
3. 为后续订阅制打下基础，优先验证留存而不是流量。

### 7.2 用户目标

1. 让用户在 3 秒内开始记录。
2. 让用户在停止录音后 60 秒内看到可读摘要与结构化结果。
3. 让用户能在 10 秒内通过搜索找回历史观点。

### 7.3 核心指标

| 指标 | 定义 | MVP 目标 |
| --- | --- | --- |
| 激活率 | 新用户在 24 小时内完成 1 次录音并看到知识卡片 | >= 60% |
| 周记录频次 | 活跃用户每周录音次数 | >= 3 次 |
| 结构化完成率 | 成功生成摘要、标签、行动项的录音占比 | >= 90% |
| 检索成功率 | 搜索后 1 分钟内点开目标内容的占比 | >= 70% |
| D7 留存 | 首次使用后 7 天仍有记录行为的比例 | >= 25% |

## 8. 产品范围

### 8.1 MVP 范围（P0）

| 模块 | 范围 |
| --- | --- |
| 账号与同步 | Sign in with Apple；单用户私有数据同步 |
| 语音记录 | 一键开始/结束录音；后台录音；离线暂存；失败重传 |
| 转写 | 中文优先，支持中英混说的基础转写 |
| 结构化整理 | 标题、摘要、关键观点、标签、行动项、主题归类 |
| 知识库 | Inbox、全部笔记、主题页、时间线 |
| 搜索 | 关键词搜索 + 向量语义搜索混合召回 |
| 回顾 | 每日回顾卡片；待确认整理项 |
| 数据控制 | 删除、导出 Markdown/JSON |

### 8.2 增强范围（P1）

| 模块 | 范围 |
| --- | --- |
| 对话问答 | 用自然语言问自己的知识库，并返回引用片段 |
| 多端查看 | Web 只读管理台 |
| 主题演进 | 自动聚合相似观点，生成长期主题页 |
| 外部导出 | 导出到 Obsidian、Notion、Readwise |
| 智能提醒 | 针对未处理想法做定时回顾 |

### 8.3 暂不纳入（Out of Scope）

1. 多人会议实时转写与说话人识别精细化处理
2. 公开社区、社交 feed、内容分发
3. 团队协作知识库
4. Android 客户端

## 9. 核心体验设计

### 9.1 核心闭环

```mermaid
flowchart LR
	A[快速录音] --> B[上传音频]
	B --> C[转写与分段]
	C --> D[摘要与观点提炼]
	D --> E[生成知识卡片]
	E --> F[搜索与回顾]
	F --> G[人工确认/合并]
	G --> H[长期主题沉淀]
```

### 9.2 关键用户流程

1. 用户打开 App，点击主按钮开始录音。
2. 结束录音后，音频本地保存并自动上传。
3. 系统生成转写、摘要、观点、标签与行动项。
4. 内容进入 Inbox，用户可快速确认、编辑、归档。
5. 结构化结果被索引到知识库，用于后续搜索与回顾。

## 11. 用户故事

1. 作为独立开发者，我希望在走路时能立即说出产品想法，并在稍后看到摘要和可执行事项。
2. 作为内容创作者，我希望把每天的语音灵感自动沉淀成可搜索的写作素材。
3. 作为管理者，我希望在会后口头复盘 3 分钟后，就能自动得到结论与待办。
4. 作为重度记录用户，我希望未来可以导出到已有知识库系统，而不是被锁在一个 App 里。

## 12. 信息架构与数据模型

### 12.1 核心对象

| 对象 | 说明 | 关键字段 |
| --- | --- | --- |
| User | 用户账户 | id, auth_provider, locale, created_at |
| CaptureSession | 一次录音会话 | id, user_id, audio_url, duration_sec, status, recorded_at |

| ActionItem | 从语音中提取的行动项 | id, note_id, content, status, due_at |
| ReviewEvent | 用户确认/忽略/合并记录 | id, target_type, target_id, action, created_at |

## 13. 推荐技术方案

### 13.1 客户端

| 层级 | 推荐方案 | 原因 |
| --- | --- | --- |
| iOS App | SwiftUI + AVFoundation + BackgroundTasks | iPhone 优先场景下，原生录音、权限、后台能力更稳定 |
| 本地缓存 | SwiftData 或 SQLite | 支持离线缓存与上传队列 |
| 崩溃监控 | Sentry | 快速发现录音和同步问题 |

### 13.2 服务端

| 层级 | 推荐方案 | 原因 |
| --- | --- | --- |
| API | TypeScript + Fastify | 开发效率高，易拆分为轻量模块 |
| 异步任务 | Redis + BullMQ | 转写、摘要、向量化均适合异步处理 |
| 主数据库 | PostgreSQL | 结构化数据与事务能力稳定 |
| 语义检索 | pgvector | 可直接与业务数据共存，降低架构复杂度 |
| 文件存储 | S3 兼容对象存储 | 保存原始音频与导出文件 |

### 13.3 AI 能力编排

1. 语音转写：优先接入成熟 ASR 服务，保证中英文混说可用性。
2. 文本结构化：调用 LLM 生成标题、摘要、观点、行动项、标签。
3. 主题关联：为知识项生成 embedding，进行近似召回和主题聚类。
4. 人工确认：高风险场景不直接覆盖用户内容，保留用户确认入口。

### 13.4 处理链路

1. 客户端完成录音并上传音频。
2. 服务端创建 `CaptureSession` 与异步任务。
3. Worker 执行转写，写入 `TranscriptSegment`。
4. Worker 执行结构化提炼，生成 `Note`、`ActionItem`、`Topic` 关联。
5. Worker 写入向量索引，标记状态为 `indexed`。
6. 客户端收到结果通知并刷新 Inbox。

| `/v1/export` | `POST` | 导出用户数据 |

## 15. 非功能需求

| 类型 | 要求 |
| --- | --- |
| 性能 | 5 分钟内音频的结构化结果在 60 秒内返回 |
| 可靠性 | 核心 API 月可用性不低于 99.5% |
| 安全 | 音频、转写、知识项均需传输加密和静态加密 |
| 隐私 | 提供删除和导出能力；后台说明模型处理链路 |
| 可观测性 | 关键任务链路需具备日志、重试、失败告警 |
| 可扩展性 | 单用户知识项达到 10 万条后仍可维持可接受搜索延迟 |

## 16. 埋点与数据分析

关键埋点事件：

- `record_start`
- `record_stop`
- `upload_success`
- `transcript_ready`
- `summary_ready`
- `note_reviewed`
- `search_performed`
- `search_result_opened`
- `export_requested`

重点分析问题：

1. 用户第一次看到结构化结果后是否愿意继续记录。
2. 用户是更依赖 Inbox 浏览，还是更依赖搜索找回。
3. 哪类结构化输出最有价值：摘要、观点、行动项还是主题页。

## 18. MVP 验收标准

1. 用户可以在 iPhone 上一键开始和结束录音。
2. 录音结束后，系统能稳定生成转写与结构化内容。
3. 用户可以在 Inbox 中查看、编辑并确认知识卡片。
4. 用户可以通过关键词找回任意历史记录。
5. 用户可以通过语义搜索找到相关观点。
6. 用户可以删除和导出自己的数据。
7. 弱网或离线场景下录音不会丢失，并可在恢复网络后继续处理。

## 19. 风险与待验证问题

1. 用户是否愿意长期使用“说出来”的方式记录，而不是仅在新鲜期使用。
2. 长语音的结构化质量是否足够稳定，是否需要用户主动分段。
3. 隐私敏感用户是否会排斥云端处理，需要评估本地模型或端侧转写路线。
4. 搜索与回顾是否真能带来复用价值，否则知识库会再次堆积。
5. 成本结构是否健康，尤其是转写、LLM 摘要和向量化的边际成本。

## 20. 下一步建议

1. 先做 10 到 20 位目标用户访谈，确认最高频记录场景。
2. 用原型验证“录音后 60 秒内看到结构化结果”的关键体验。
3. 尽快做一个 concierge MVP，手动辅助结构化，先验证留存与复用率。
4. 如果验证通过，再投入自动聚类、主题演进和问答式检索。
